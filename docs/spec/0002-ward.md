# ward: a session gets a secret without seeing it

Status: Draft: in force only when the owner merges it. Revision 2, after spec
review round 1.

This spec adds a skill, `ward`, that tells a session how to start one program
with an API key or a token from a password manager in its environment. The
session never sees the value. Each call gives a reason, and the owner tracks
agents by those reasons. Tier: thorough, on the sensitive route: the skill
handles credentials. The security pair reads this spec and the diff.

A tag names where a choice comes from. `W1` to `W3` are the owner's words
(S1). `R1` names the first round of questions and `R2` the second; the owner
answered both, relayed by the lead. `P1` to `P6` are this revision's picks
that change or narrow an R1 or R2 answer, each brought to the owner (S16). A
choice with no tag is this spec's own.

**Outside sources.** Three managers inject this way: Proton Pass's `pass-cli

https://protonpass.github.io/pass-cli/commands/agent/).

## S2. Objective

Sessions today do not know a password manager is there for them. They look for
a key in environment variables, give up, or ask the owner. The owner then
reminds them (W1).

After this change, a session that needs a secret loads `ward` unasked. It reads
the person's local file, writes one env file of references, and starts the one
program that needs the secret through the person's wrapper. The manager puts the
value into that program's environment. The session and its transcript never
hold the value. The program does, and S5 limits which program that is.

Who uses it: every session that needs an API key or a token, and the person
who owns the vault and reads the reasons. In this spec, "the owner" is that
person.

## S3. Terms

- **The wrapper:** the owner's own script around the manager's command-line
  tool. It supplies the manager's credential to the tool and may mask output
  that can hold a value. It is the owner's file, outside the repository.
- **A reference:** the manager's address of one field, such as
  `<scheme>://<vault>/<item>/<field>`. A reference is not a secret, but it
  names the owner's vaults and items, so it is a private detail.
- **The map:** the local file's table from a secret's name (the variable a
  program reads) to its reference and the service it is for.
- **The reason:** the text the session puts in the reason variable before each
  call.
- **The child:** the program the manager starts with the secret in its
  environment.

## S4. The skill's procedure

`skills/ward/SKILL.md` directs these steps, in this order. Every command is
written for a POSIX shell (`sh` or `bash`; Git Bash on Windows). The skill
directs no PowerShell or `cmd` form.

1. **Read the local file** at `~/.grimoire/ward/config.json`, `~` being the
   home folder from the environment. When it is missing or does not parse,
   tell the owner in one line, name the example
   (`references/config.example.json` in the skill's folder) and stop (C8).
   Never write or fix the file.
2. **Check the file** before the first call (C11). Each map name matches
   `^[A-Z][A-Z0-9_]*$`. Each reference matches S10's reference pattern. No
   argument list in the file holds an act S5 or the file's own `forbidden`
   names. When a check fails, tell the owner which field and stop, quoting no
   value.
3. **Check the session folder variable** that the file names, printing only
   whether it is set: `[ -n "${NAME+x}" ] && echo set || echo unset`. When it
   is unset, tell the owner in one line and stop. Never set it.
4. **Find the name in the map.** When the name is missing, tell the owner the
   name and the service it is for, and stop (C6, P4). The session runs no
   listing or search of the vault.
5. **Write the reason** in the session's own words, as
   `<session label or issue key>: <what for>, <service>`, at most 300
   characters (C2). It holds no secret, reference, path, personal detail, or
   text copied from a tracker, a file or another session. It holds no quote,
   `$` or backtick. It is set for the one call, single-quoted:
   `NAME='<reason>' <wrapper> ...`.
6. **Write the env file** in the temporary folder the session's instructions
   name, else the system's (`${TMPDIR:-/tmp}`), with a name unique to this call
   (`ward-<8 random hex>.env`). One line `NAME=<reference>` for each secret that
   one command needs, and nothing else (C3).
7. **Run the child** with the wrapper, the file's `runSeparator`, and the
   scrub step (C3, C10):
   `<wrapper...> run --env-file <file> <runSeparator> env -u <V1> -u <V2> <command...>`,
   with one `-u` for each variable in the file's `childUnset`. The session
   adds no other flag.
8. **Delete the env file** when the command ends, whether it passed or failed
   (C3).
9. **On an auth failure,** which is a non-zero exit whose output names a
   login, a session, auth, a token or "unauthorized": run `<wrapper...> info`
   once, quoting none of its account details. When the file holds `login`, run
   it once, with a 60-second limit (`timeout 60`). Then retry the call once.
   When that fails too, or the file holds no `login`, tell the owner in one
   line and stop (C5, P3). The session never starts a web login, never passes
   a token, and never repeats a login URL or code it sees.

Any other failure: one line to the owner, then stop. Every call is visible to
the owner, so the session plans each call before it makes it, runs only the
calls these steps name, and never tries commands to see what works (C12).

The fixed verbs (`run`, `--env-file`, `info`) and the scrub step live in
`SKILL.md`, not in the local file, so a changed file cannot change what is run
beyond its named fields.

## S5. The forbidden list

`SKILL.md` names each of these acts and forbids it (C4):

- printing, writing, logging or returning a secret's value, in any form,
  encoded or in part;
- a flag or variable that turns masking off or reveals values, such as
  `--no-masking`, `--show-secrets`, and any the local file's `forbidden` names;
- a manager command that prints a value or writes it to a file: viewing an
  item (`item view`), injecting into a file (`inject`), the manager's `export`
  verb, and a one-time code (`totp`);
- a token or password on a command line;
- a child that prints its environment or a variable from it, such as `env`
  with no command, `printenv`, or a shell or interpreter one-liner that the
  session writes around the variable;
- the secret in the child's own argument list: the child reads it from its
  environment;
- a child run with a verbose, debug or trace flag;
- a child that saves a credential, such as a login command of another tool;
- a child the session did not choose for this task: a package install, a
  lifecycle or test script, a build, or code from a clone, a pull request, a
  tracker or another session's message (P2);
- a child that sends the secret anywhere but the map's service for it, or over
  anything but TLS (P2);
- quoting a reference, an item's title, the wrapper's name or a variable from
  the local file in a post, a report, a commit or a record.

The local file's `forbidden` adds the acts particular to the owner's wrapper.
The skill obeys both lists.

## S6. The local file

The file lives outside the repository, at `~/.grimoire/ward/config.json`,
UTF-8 JSON. Its fields:

| Field | Holds |
| --- | --- |
| `wrapper` | An argument list: the command that runs the wrapper |
| `runSeparator` | The token the wrapper takes before the child: `--`, or `---` for a wrapper whose shell swallows a bare `--` |
| `reasonVariable` | The variable the wrapper reads the reason from |
| `sessionFolderVariable` | The variable that names the manager's session folder |
| `childUnset` | The variables the child must not inherit: the manager's credential variables and the session folder variable |
| `login` | Optional. An argument list after the wrapper that logs in with no prompt and no token in it |
| `forbidden` | `{ "flags": [], "variables": [], "commands": [] }`: the wrapper's own extra forbidden acts, such as its reveal variable |
| `secrets` | The map: `{ "<NAME>": { "ref": "<reference>", "service": "<host>" } }` |

`skills/ward/references/config.example.json` holds the same fields with
placeholders only (C7). No shipped file names a real manager's variable, a
real vault, item or field, or a real service's key name.

## S7. This machine's local file (R2, P4)

Ticket T2 writes `~/.grimoire/ward/config.json` on the owner's machine,
outside the repository, before Test. It takes the wrapper, the variables, the
separator and the forbidden acts from the wrapper's own text and the tracker's
notes. It runs no vault listing (P4): the owner gives the one reference Test
needs, through the lead, or adds it to the file. Done means the file parses,
passes S4 step 2's check, and holds every S6 field but the optional `login`
(P3). T2 then reads the folder's access list (`icacls` on Windows, `ls -ld`
elsewhere) and tells the owner whether anyone but the owner, the system and
administrators can read it. Nothing from this file enters the repository, the
spec, the pull request or a public record; the machine's own detail stays in
the private tracker.

## S8. What ward takes from one manager's guide (R2)

`SKILL.md` cites Proton Pass's agent guide as a source and takes one step from
it: on an auth error, check the session with `info`, log in again, and retry
(S4 step 9). It copies no text from it: the guide states no licence. It does
not take the guide's way of reading a value (`item view`) or of logging in (a
token on the command line), which S5 forbids.

## S9. Acceptance claims

- **C1.** A session that needs an API key or a token loads `ward` unasked: the
  description names that need.
- **C2.** Every wrapper call `SKILL.md` directs sets the reason variable for
  that call, in S4 step 5's shape and limits.
- **C3.** A secret reaches a program only through S4 step 7's run shape, with
  one uniquely named env file of references for one command, deleted after the
  command ends.
- **C4.** `SKILL.md` names and forbids each act in S5.
- **C5.** On an auth failure: `info` once, the file's `login` once if it holds
  one, one retry, else the owner is told. No web login, no token passed.
- **C6.** A name missing from the map: the owner is told the name and service,
  and the session makes no vault call.
- **C7.** The repository holds no owner detail: the example file holds
  placeholders only, and no shipped file names a real wrapper, variable,
  vault, item, field or service key.
- **C8.** A missing or broken local file: one line to the owner naming the
  example, and no further call.
- **C9.** On the owner's machine, one real run of a harmless child that prints
  nothing leaves a record the owner can read: the reason, at the call's time,
  in the manager's audit log. Pass: the owner finds it. Fail: the owner does
  not.
- **C10.** A child started by S4 step 7 holds none of the `childUnset`
  variables.
- **C11.** A local file that fails S4 step 2's check stops the session before
  any wrapper call, with the field named and no value quoted.
- **C12.** A session following the skill makes no call outside S4's steps,
  and repeats none.

## S10. How the claims are checked (R2)

- **One test file,** `tests/ward.test.mjs`, on `node --test`, backs C4 and C7.
  - It parses the example file.
  - A placeholder is a whole string, or a `/`-separated segment, of the form
    `<…>`. Every string value in the example file is a placeholder, except
    `runSeparator` (`--`), `{envFile}` and `{command}` if used, and the
    `forbidden` keys.
  - A reference is a string matching `^[a-z][a-z0-9+.-]*://` whose scheme is
    not `http` or `https`. Every reference in the example is placeholders after
    the scheme; no file under `skills/ward/` holds a reference with a segment
    that is not a placeholder.
  - `SKILL.md` contains each of these strings: `--no-masking`,
    `--show-secrets`, `item view`, `inject`, `export`, `totp`, `printenv`,
    `env -u`, `on a command line`, `argument list`, `verbose`, `TLS`,
    `package install`, `forbidden`.
  - When the owner's `~/.grimoire/ward/config.json` exists, the test also
    fails when any of its string values longer than three characters appears
    in a file under `skills/ward/`, in `README.md`, in
    `.claude-plugin/plugin.json` or in this spec. It names the file and the
    field, never the value. It skips this check when the file is missing, as in
    CI and the container.
  - Each check fails when its rule breaks.
- **The dry run** (Test, ticket T3). A fresh session, with `ward` installed
  from the branch and the owner's real file, takes two tasks. Its wrapper calls
  are real, with reasons, and are signed off with this spec.
  - Task A: start the harmless child of C9 with the reference the owner gave.
    The transcript is read against C1, C2, C3 and C12.
  - Task B: a task that needs a secret name the map lacks. The transcript is
    read against C6 and C12.
- **C5, C8 and C11** are checked by reading `SKILL.md`'s steps against each
  claim's text. Breaking the owner's file or login to test them is not cheap to
  reverse.
- **C9.** T3 runs the call with the child `sh -c 'exit 0'`, which reads no
  variable, and hands the owner the call's UTC time and the exact reason. The
  owner reads the audit log in the Test stage, before the pull request is
  marked ready. On a fail, `SKILL.md` gains this line: "The manager may record
  no reason for `run`; the session's reason then reaches no audit log." The
  owner's next step is a new issue (S14).
- **C10.** T3 runs one call whose child prints only whether each `childUnset`
  variable is set: `sh -c 'for v in V1 V2; do eval "[ -n \"\${$v+x}\" ]" && echo "$v set" || echo "$v unset"; done'`,
  with the variable names filled in. Pass: every one prints `unset`.
- **The repo's check,** `athanor run check` (or the host check where athanor
  is missing), is green on the branch.

## S12. Boundaries and security

- **Always:** the reason on every call; one command per uniquely named env
  file; the file deleted after; the scrub step; the owner told in one line,
  then stop, on any failure the procedure does not handle.
- **Ask first:** none at run time. The skill never asks the owner for a value.
- **Never:** the acts in S5; writing to the local file or the wrapper; any
  call outside S4's steps.

Where data goes, for the owner to accept (P6):

- **The transcript** holds the local file's contents when the session reads
  it: the wrapper's name, the variables and every reference. The transcript
  goes to the model provider, to every device signed in to Remote Control, and
  to the transcript file on disk.
- **The reason** leaves the machine: the manager sends it to its service's
  audit log. S4 step 5 keeps secrets, references, paths and personal details
  out of it.
- **The secret** goes to the child and whatever the child sends. S5 limits the
  child to a program the session chose, sending to the map's service over TLS.

What holds, and what does not:

- **The manager's credential.** A wrapper that hands the manager its token in
  the environment passes it to the child too, unless the scrub step removes it.
  `childUnset` and C10 hold this. The manager's own access grants for the
  agent bound what any leak can reach; scoping them to the map's items is the
  owner's act, outside this change (P1).
- **Masking** is the manager's, exact-match, on the child's stdout and stderr
  only. An encoded value, a value in a file the child writes, and a value in an
  argument list pass it. S5 forbids each; those rules are prose.
- **More reach to a session** (P2). A session steered by outside text, or
  running code it did not write, can start a child with a secret. S5's child
  rules are prose, which the class "Text steers a session" says break. The
  added reach fits no accepted class, so the owner decides it.
- **The local file is an input** that every session obeys. A session that
  writes it once changes later sessions' calls. S4 step 2's check and the fixed
  verbs narrow what a changed file can do; the write itself is held by the
  harness's prompt only.

## S13. Trade-off points

- **Security against traceability.** `run` keeps the value out of the
  transcript, but a manager may not record `run` in its audit log, so a misuse
  through `run` could leave no record. Side taken: security (`run`), with C9 to
  learn what the record shows; a fail makes it the owner's security decision.
  Driver: the issue asks that no value be shown, and W1 asks for the reason.
- **Generality against fit.** The skill is for any manager with a `run`-style
  injector; the owner's file carries the fit. Driver: grimoire is public.
- **Business driver:** none named in AGENTS.md or this spec. The lean is to
  what is cheaper to reverse.

## S14. Out of scope

- Sigil art for the README (a follow-up if wanted).
- Eval cases for ward's model behaviour.
- A change to the owner's wrapper. If C9 fails, or the owner prefers the
  wrapper to drop its token before `run`, that is a new issue.
- Removing env files left by a killed session: an accepted-risk candidate
  (the file holds references, not values, and stays on the machine).
- Writing or rotating secrets in the vault.
