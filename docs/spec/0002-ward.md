# ward: a session gets a secret without seeing it

Status: Draft: in force only when the owner merges it.

This spec adds a skill, `ward`, that tells a session how to get an API key or a
token from the owner's password manager. The session never sees the value. Each
call gives a reason, and the owner tracks agents by those reasons. Tier:
thorough, on the sensitive route: the skill handles credentials. The security
pair reads this spec and the diff.

A tag names where a choice comes from. `W1` to `W3` are the owner's words
(S1). `R1` names the first round of questions and `R2` the second; the owner
answered both, relayed by the lead. A choice with no tag is this spec's own.

## S1. Sources

**The owner's words,** said by voice to the lead on the day the work was filed:

- **W1**: "You are forced to give … a reason whenever you use it, and that's
  how I track you with it. … How can I stop reminding you of that?"
- **W2**: "something like a skill that directs you on how to use it."
- **W3**: "you could start it at the Thorough Sensitive Tier."

**R1** settled: the skill's name; any password manager whose command-line tool

the forbidden list; one listing for a name missing from the map; the reason's
shape; one login and one retry on an auth failure.

**R2** settled the claims (S9), how they are checked (S10), who writes the
owner's local file (S7), what ward takes from Proton's guide (S8), how the
record is checked (S10, C9) and the repository surface (S11).

**Outside sources.** Proton Pass's CLI ships an agent guide
(`pass-cli agent instructions`, and the page at
https://protonpass.github.io/pass-cli/commands/agent/). Bitwarden's `bws run`
and 1Password's `op run` inject the same way ward does.

## S2. Objective

Sessions today do not know a password manager is there for them. They look for
a key in environment variables, give up, or ask the owner. The owner then
reminds them (W1).

After this change, a session that needs a secret loads `ward` unasked. It reads
the owner's local file, writes one env file of references, and starts the one
program that needs the secret through the owner's wrapper. The manager puts the
value into that program's environment. The session, its transcript and the disk
never hold the value.

Who uses it: every session that needs an API key or a token, and the owner, who
reads the reasons.

## S3. Terms

- **The wrapper:** the owner's own script around the manager's command-line
  tool. It supplies the manager's credential to the tool and masks output that
  can hold a value. It is the owner's file, outside the repository.
- **A reference:** the manager's address of one field, such as
  `pass://<vault>/<item>/<field>`. A reference is not a secret, but it names
  the owner's vaults and items, so it is a private detail.
- **The map:** the local file's table from a secret's name (the variable a
  program reads, such as `TYPESAFE_API_KEY`) to its reference.
- **The reason:** the text the session puts in the reason variable before each
  call.

## S4. The skill's procedure

`skills/ward/SKILL.md` directs these steps, in this order:

1. **Read the local file** at `~/.grimoire/ward/config.json`. When it is
   missing or does not parse, tell the owner in one line, name the example
   (`references/config.example.json` in the skill's folder) and stop (C8).
   Never write or fix the file.
2. **Check the session folder variable** that the file names. When it is not
   set in the session's environment, tell the owner in one line and stop.
   Never set it.
3. **Set the reason** on every wrapper call, as
   `<session label or issue key>: <what the secret is for>`, at most 300
   characters (C2). The reason holds no secret and no reference.
4. **Find the name in the map.** When the name is missing, run one listing of
   items with the reason set, never with a flag that adds values, then tell
   the owner which reference to add and stop (C6).
5. **Write the env file** in the session's temporary folder (the job's
   temporary folder when the harness names one, else the system's), one line
   `NAME=<reference>` for each secret that one command needs (C3). Nothing
   else goes in it.
6. **Run the program** with the file's run shape, such as
   `<wrapper> run --env-file <file> <separator> <command>` (C3).
7. **Delete the env file** when the command ends, whether it passed or failed
   (C3).
8. **On an auth failure,** run the file's info command once, then its login
   command once, with no token typed or passed, then retry the call once. When
   that fails too, tell the owner and stop (C5).

The skill also states that every call is visible to the owner. A session plans
the call before it makes it, and never tries commands to see what works.

## S5. The forbidden list

`SKILL.md` names each of these acts, and forbids it (C4):

- printing, writing, logging or returning a secret's value, in any form,
  encoded or in part;
- a flag or variable that turns masking off or reveals values, such as
  `--no-masking`, `--show-secrets`, or the reveal variable that the local file
  names;
- a command that prints a value or writes it to a file: viewing an item
  (`item view`), injecting into a file (`inject`), `export`, and a one-time
  code (`totp`);
- a token or password on a command line;
- a child program that prints its environment or a variable from it, such as
  `env`, `printenv`, `set`, or a shell or interpreter one-liner that the
  session writes around the variable;
- a child program that sends the secret anywhere but the service the secret is
  for.

The local file's `forbidden` list adds the acts that are particular to the
owner's wrapper. The skill obeys both lists.

## S6. The local file

The file lives outside the repository, at `~/.grimoire/ward/config.json`,
UTF-8 JSON. Its fields:

| Field | Holds |
| --- | --- |
| `wrapper` | The command that runs the wrapper |
| `reasonVariable` | The variable the wrapper reads the reason from |
| `sessionFolderVariable` | The variable that names the manager's session folder |
| `run` | The run shape, as an argument list with `{envFile}` and `{command}` |
| `info` | The argument list that shows the session's state |
| `login` | The argument list that logs in again, with no token in it |
| `forbidden` | Extra forbidden flags, variables and commands |
| `secrets` | The map, from a name to a reference |

`skills/ward/references/config.example.json` holds the same fields with
placeholders only: no real wrapper name, variable name, vault, item or field
(C7).

## S7. This machine's local file (R2)

This session writes `~/.grimoire/ward/config.json` on the owner's machine,
outside the repository, from the wrapper's own text and the issue's notes. It
finds the TypeSafe reference by one listing of items, with the reason set and
no flag that adds values. Nothing from this file enters the repository, the
spec, the pull request or a public record. The file stays readable by the
owner's account only, as the other files in the owner's home are.

## S8. What ward takes from Proton's guide (R2)

`SKILL.md` cites the guide as a source. It takes two steps from it: check the
session with `info` before use, and on an auth error log in again and retry.
It copies no text from it: the guide states no licence. It does not take the
guide's way of reading a value (`item view`) or of logging in (a token on the
command line), which S5 forbids.

## S9. Acceptance claims

- **C1.** A session that needs an API key or a token loads `ward` unasked: the
  description names that need.
- **C2.** Every wrapper call `SKILL.md` directs sets the reason variable, in the
  shape `<session label or issue key>: <what for>`.
- **C3.** A secret reaches a program only through the run shape, with one env
  file of references for one command, deleted after the command ends.
- **C4.** `SKILL.md` names and forbids each act in S5.
- **C5.** On an auth failure: info once, login once with no token typed, one
  retry, else the owner is told.
- **C6.** A name missing from the map: one listing with no value flag, then the
  owner is told which reference to add.
- **C7.** The repository holds no owner detail: the example file has
  placeholders only, and no shipped file names the owner's wrapper, its
  variables, or a vault, item or field.
- **C8.** A missing or broken local file: one line to the owner naming the
  example, and no further call.
- **C9.** On this machine, one real run of a harmless program, which prints
  nothing, with the TypeSafe reference, leaves a record the owner can read.
  The owner reads Proton's audit log (agent monitor or the app) and says
  whether the reason is there.

## S10. How the claims are checked (R2)

- **One test file,** `tests/ward.test.mjs`, on `node --test`, backs C4 and C7.
  It parses the example file and checks each field is present; it checks each
  reference in it is a placeholder (`<…>` segments only); it checks every other
  field's value in it is a placeholder too; it checks no file under
  `skills/ward/` holds a reference that is not a placeholder; and it checks
  `SKILL.md` names each act in S5. Each check fails when its rule breaks. A
  test cannot name the owner's wrapper or variables without publishing them, so
  the rest of C7 (no shipped file names them) is held by the read before
  posting and by the review of the diff.
- **C1, C2, C3, C5, C6 and C8** are what a model does. A fresh session at Test
  takes a dry-run task that needs the TypeSafe key, with `ward` installed from
  the branch, and the transcript is read against each claim. No eval cases are
  added, so no eval budget changes.
- **C9** is checked once at Test by the real call, and the owner reads the
  record. When the run leaves no reason, the skill says so in one line, and the
  owner decides what follows (S13).

## S12. Boundaries and security

- **Always:** the reason on every call; one command per env file; the file
  deleted after; the owner told in one line, then stop, on any failure the
  procedure does not handle.
- **Ask first:** none at run time. The skill never asks the owner for a value.
- **Never:** the acts in S5; writing to the local file or the wrapper; any
  call outside S4's steps.

Places the security pair should read first:

- **The reason leaves the machine.** The manager sends it to its own service's
  audit log. S4 step 3 keeps a secret and a reference out of it; the session
  label and the purpose still go.
- **More reach to a session.** A session that reads outside text can now start
  a program with a secret in its environment. S5's last two bullets are prose
  rules. The threat model's class "Text steers a session" names that prose
  rules break; this spec brings the added reach to the owner as a checkpoint.
- **Masking is the wrapper's and the manager's.** `run` masks a value the child
  prints, by the manager's own masking. Ward does not rebuild that control.
- **The env file holds references,** private details, for one command's
  length, in the session's temporary folder.

## S13. Trade-off points

- **Security against traceability.** `run` keeps the value out of the
  transcript, but Proton's docs list the audited actions without `run`, so
  the owner's record may miss a run. Side taken: security (`run`), with C9 to
  learn what the record shows. Driver: the issue's ask for injection (W1 asks
  for the reason; the issue asks that no value be shown).
- **Generality against fit.** The skill is for any manager with a `run`-style
  injector; the owner's file carries the fit. Driver: grimoire is public.
- **Business driver:** none named in AGENTS.md or this spec. The lean is to
  what is cheaper to reverse.

## S14. Out of scope

- Sigil art for the README (a follow-up if wanted).
- Eval cases for ward's model behaviour.
- A change to the owner's wrapper, such as a log line of its own. If C9 shows
  no reason for `run`, that is the owner's next choice.
- Writing or rotating secrets in the vault.

## S15. Open questions

- **The login command on this machine.** The tool's `login` defaults to a web
  login when no token is passed. Whether the wrapper's call logs in from the
  token it supplies is not yet known. S7 writes `login` as the tool's plain
  `login`; Test learns whether that works, with no token typed.
- **Whether `run` leaves a reason** in the audit log (C9).
