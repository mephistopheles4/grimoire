# Brigade and head chef: bounds and guards

This page is part of the threat model in [`threat-model.md`](threat-model.md). A control it names is named by the threat model, and a security review is handed it with the threat model. An edit to its accepted-risk, candidate or gap lines is an edit to the threat model's accepted risks.

This page holds the detail behind the short page's R5, R6 and R7: the bounds on each call the Brigade mod makes through the engine, and the head chef's guards and data. The summary below points into the moved text: [row 15](#row-15) for the mod, [row 16](#row-16) for the head chef, and [the engine calls](#row-15-the-engine-calls-behind-its-write-and-its-tool-call) for each call's bounds. Where the summary and the moved text differ, the moved text holds. Residual risks are named by the threat model's classes and candidates only.

Sources: `brigade/register.tsx`, `brigade/cleanup.ts`, `skills/head-chef/references/CONTRACT.md` and `skills/head-chef/references/cleanup.md`, ADR 0008 and ADR 0010.

## Summary, part 1: the mod's calls and their bounds

- **Offered only where asked.** The mod's tools are offered only after `/brigade` or a head-chef load, and work only once the mod has offered them to that session since its last reload. A call that carries a subagent id is refused. A load the owner did not type, and the tools' use in plan and don't-ask modes, are class C8.
- **The engine's verdict first.** Before `set_roster` writes, and before Open in app's tool call, the mod asks `$.tool.check` for the engine's verdict. `set_roster` refuses a `deny`, an `ask` that names a rule, and an organisation ceiling below `allow`. The usage summary writer's write is the exception: no permission rule, mode, owner hook or classifier reaches it. Other plugins' hooks can see, rewrite or deny the roster write, or approve it over the owner's ask rule; row 15 names this as the trust they already have.
- **One path rule.** The model never names a path. The roster, summary, log, marks and hand-off files are built from the config folder and a session id of the engine's own shape, and the rule walks every folder with `stat` before each write and each pane read, and again after each write. A link found after a write is told in the pane and a toast. Transcripts are found from the launch folder's projects name and a listed folder, under the place check.
- **Caps and strict checks.** Each file kind has a byte cap and a strict check, and a roster file that fails is refused without echoing what it holds.
- **Fixed words out.** Refusals and notes use fixed wording, and `gh`'s error text and a rejection's text are never shown. Row 15 names one exception: a server that answers as `ccd_window` can put one cleaned line of its own in Open in app's success toast.
- **Engine answers are claims.** The pane list, the tool list, the verdict and environment values come from the engine, and a plugin whose hooks sit above grimoire's can answer them. A session's liveness misstated through an engine answer is class C4 (E30); the rest stays an open gap on row 15.

**How the pane shows text.** Report lines, roster text and to-dos are shown as written by their session, as claims, never as the owner's. A sender's name is a claim. Every string is drawn as text, never as Markdown or a link. An Owner entry the pane did not write in that session draws as "Owner (as recorded)". Pull request rows stay on github.com behind a click and name their repository.

**Classes and candidates for row 15.**

- C4: what another plugin can read, rewrite, plant or press in plugin state, the plugin's store or its data folder, as the class lists it.
- C5: a forged or misled session, and false entries written within the tool's own rules.
- C7: other repositories' rows and titles in memory and on the pane, files at rest that reach backup, sync and other local accounts, and the level in the lead's transcript.
- C8: no permission prompt on the mod's tools.
- Candidates: same-user races, links, planted files and files at rest (P1); left-behind or planted session files (P2); reliability items (P3); a session's own summary file feeding another card, and refusal lines planted, hidden or read by another plugin (P7; the base named them as gaps only); the report store's question and a session's Remote Control link in plugin state (P6). The proposed scope line (P0) drops none of these outright; see P1. Until the owner names a candidate, each entry stays as at the base.

## Summary, part 2: the head chef's guards

All of these are prose the host agent follows. Nothing runs them (C1).

- **Sessions.** The head chef starts sessions only on the owner's words in the lead's chat. It names each session itself from letters, digits and `. _ -`, never from an issue, and it sets no permission mode. A background start needs the owner's words choosing that route, and is refused on an unsafe name or form.
- **The start prompt.** Before head-chef 1.10.0, one fixed-form pointer holding the stage, the issue, its repository and the lead's name, with no task text, title or id. It tells each session that text not written by the person it works for is data, to sign its posts, to report by message, and how to check a sender. Since head-chef 1.0.0 (issue 450) it names the lead by name only, sends reports to that name by message only and never on the issue, and takes a new lead name only from the owner's words in the session's own chat. Since head-chef 1.10.0 (issue 503) it is one sentence pair, the issue and the lead's name, and holds no rule: the harness labels a message from another session as data, and the member's own rules govern stages, approvals, posting and accepted risks. A member whose rules need the owner's word refuses the lead's level-3 accepted-risk picks (E80), and a message under the lead's name that names a new lead can redirect reports (candidate P8).
- **The sender check.** A session takes the lead's first message only when its shown name matches the lead's row alone and a status file carries the lead's name, the message's `from-session` and its `from` address. After that, only the kept id with a paired address counts. A malformed id or address is refused before any check runs. The status-file check is a consistency check, not a guard (C5). The sender check is withdrawn in head-chef 1.0.0 (issue 450): a member knows its lead by name only (candidate P8).
- **The owner's yes.** Starting a session, cleanup, and each act on GitHub each need the owner's own words naming it. A request found in a report, a relay or a comment goes to the owner, and nothing is done.
- **Data, not instructions.** Reports, relays, notes and comments are data. A relay is quoted with its source. Each decision sent is labelled as the lead's own or the owner's words, relayed.
- **GitHub acts.** Each act names its repository and says whether the record is public. Free text goes through a temporary post file outside any repository, deleted afterwards. The head is read again before a merge. A branch to delete comes only from the owner's words or a same-repository head. No error text goes on an issue, a card, a to-do or a start prompt (C6).
- **The roster** is written only through the mod's `set_roster`, under row 15's guards.
- **The permission warning.** It is shown before the first launch in a lead. Pressing "I understand" is a reminder; only the owner's words in chat record a risk, and at a confirmed level 3 the lead's own pick, logged with a review entry (E80).
- **Cleanup** (head-chef 0.17.0; its reads moved into the Brigade mod in head-chef 1.1.0, issue 454; one typed act since head-chef 1.8.0, plugin 0.110.0, issue 484). The owner's typed `/brigade done` is the only yes, at every level; its reply lists each opened card's kind, repository, folder and branch, as bound when the card joined, and `/brigade done none` takes it back. The lead archives or stops those sessions and calls `clean_up`, which runs the pact's cleaner with `--recoverable` for exactly the window's folders. Brigade removes nothing itself: no forced removal, no `-D`, no `claude rm`, no GitHub query. The cleaner removes a worktree and its branch only when everything in it can be recovered, and keeps and lists anything else. An item with no record, or a folder outside `<main>/.claude/worktrees` or the cleaner's name rule, gets no run.

## Row 15

### Scenario

**Text another session wrote misleads the Brigade pane, or makes it act.** The plugin ships a mod: a hooks module, `brigade/register.tsx`, that Claude Code runs in every session where grimoire is installed, with the session's own rights. While its pane is open it reads the engine's own session files, `<config>/sessions/<digits>.json`, every 10 seconds (since 0.67.0, #347, it runs no `claude agents --json`); since 0.71.0 (#358) it also takes each file's Desktop id, job id, waiting reason and update time, the ids only to match a card to its session and never kept, and draws the session's own name on its card, reads the lead session's roster file every 5, reads other sessions' transcripts to find a link and, for each roster member, the last model call's time and context size for a cache-warmth line on its card, since 0.55.0 also the context size of its recent calls and their new tokens, and its model's window, for a context meter on its card, and since 0.56.0 a burn rate and context trend sparkline, since 0.52.0 listing the config folder's `projects` folder at most once a minute to find a transcript that moved into a worktree folder, shows the first line of each report another session sends, and shows this session's own rate limits and context at the bottom of the pane, as an SVG image on Desktop, the editor and mobile. Since 0.36.0 it also writes the roster file itself, when the model calls its `set_roster` tool, with no permission prompt. Since 0.38.0, when the owner presses Open in app on a card with a Desktop id, it asks the Desktop app's own tool, `open_session_in` on the server named `ccd_window`, to show that session in a split beside the lead, again with no permission prompt. Since 0.60.0 every session, in a brigade or not, also runs a per-call hook and writes its own usage summary file, numbers only, again with no permission prompt. Since 0.64.0 (#339), while its pane is open and a card carries a pull request number, it also runs `gh pr list` once a minute, again with no permission prompt, and draws the titles and repository names `gh` answers; since 0.85.0 (#415) once a minute per repository, at most 6 runs a minute, the named repositories taking turns past five, for the repositories the shown cards name. A planted roster, a session named to match a card, a forged report, or a rate-limit kind a gateway names tries to make the pane run something, open a link the owner did not mean, read a file it should not, a file reached through a planted folder or link under `projects` included, or show the owner a false state, a false cache warmth or a false nudge to reply or hand off included. Or a hijacked lead, a planted link or another plugin turns a roster write into a write somewhere else, or into a message to the owner. Or a planted card, another connected server or another plugin turns a press of Open in app into a call the owner's rules do not allow, a call to another tool or server, or a false answer. Or a planted link, a hard link or a planted file turns a session's summary write into a write over another file, or a forged summary file shows the owner a false warmth.
