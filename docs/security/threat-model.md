# Threat model

This page lists the attacks worth planning for, what stops each one today, and
what still gets through. Each row is a scenario told from the attacker's side.
The framework labels are tags, so a reader who thinks in STRIDE or MITRE ATLAS
can find their way in. [`SECURITY.md`](../../SECURITY.md) is the summary.

## What an attacker can reach

grimoire runs nothing on a server. An attacker reaches a user through one of
five doors:

1. **A file they wrote** — a box or flightpath file, a skill or agent file
   and its contract, an interview draft or the answer block pasted back from
   the contract skill's hiring page, or the pull request, ticket or diff an
   agent is asked to chart.
2. **The skill prose itself** — a change to a `SKILL.md` that reaches every
   installer on the next update.
3. **The CI and publishing path** — the workflows and the actions they run.
4. **The edge audit** — the one script that sends text and a key off the
   machine, apart from the Brigade pane's `gh` call (door 5), which runs the
   owner's own GitHub command line tool and sends its credential to GitHub
   at most once a minute while the pane is open and a shown card carries a pull request.
5. **The Brigade mod** — the hooks module Claude Code runs in every session
   that has the plugin, and the text it reads from other sessions.
6. **The head-chef skill's brigade** — the sessions the skill starts, the
   reports and relays they send back, and the worktrees it deletes.

Behind every door the target is the same: **an agent on the user's machine
that obeys text.** The browser page matters too, but it is the smaller prize.

## Likelihood and impact

The chart places each scenario in [the matrix](#the-matrix) below by its
**residual** risk: what is left after today's guards. The numbers are
judgement, not measurement, and they are here to rank the scenarios, not to
score them.

- **Likelihood** asks how easy the attack is and how often the path occurs. A
  pull request anyone can open scores high. A stolen maintainer token scores low.
- **Impact** asks what the attacker gets. Control of an agent on many machines
  scores highest. A wrong error message scores lowest.

How to read it:

- **Act now (top right): row 1.** Anyone can open a pull request, and charting
  one is what groundtrack is for. Gap 1 below narrows it most; gap 3's
  reminder narrows it too, but binds no one, so it stays here.
- **Guard closely (top left): rows 2, 13, 16, 8, 14, 9, 10, 15 and 3.** Rarer, but
  severe. Row 2 is row 1's quieter twin, narrowed by the same gap. Row 13 is
  row 2 for the contract skill, plus a validator pass that can be read as a review.
  Row 16 is row 2 for the head chef, whose agent can start sessions and
  delete worktrees; its guards are prose, and two of git's own refusals.
  Row 8 moved left once the scanners became required checks (gap 2). Row 14
  sits at row 8's likelihood: the skill under test is the owner's own, and
  the tester writes the planted lines. Its guard is hygiene, not a boundary.
  Row 15 moved here from Accept once the mod began writing the roster
  itself: an injection can now reach a silent write that addresses the
  owner, and the race between the mod's check and its write can reach
  another file. Since 0.38.0 a press of Open in app also makes a tool call
  that no permission prompt sees, so the owner's rules over it hold only
  through the mod's own checks.
- **Watch (bottom right): row 12.** It happens by design whenever an account
  has logging on, and the harm is bounded to text the user chose to send.
- **Accept (bottom left): rows 4, 5, 6, 7, 11, 17 and 18.** Row 6 sits nearest the
  middle and gap 1 narrows it. Row 17's pull request needs a reviewer to miss an ignore
  line, and the check now fails what it hides; its home paths are slips the
  check catches in the common shapes.

## Row 5, measured

**The renderer's three commands finish in under 1.5 s on every file measured,
up to 25 MB, that passes the three limits.** The target is 3 s for each of `--check`, `--out` and `--text`. The
page's first draw is not held to that target. A page of 20,000 separate boxes
takes about 6 s, and nearly all of it is the browser building the boxes.

All numbers were measured with `fold` sharing its tables between moves (#145).
Each file below is the worst one measured that passes every limit, for the
cost it drives.

| Cost it drives | Worst passing file | `--check` | `--out` | `--text` | Page, first draw |
| --- | --- | --- | --- | --- | --- |
| Call depth (limit 1,000 calls) | A chain of 1,001 nodes, 1,000 calls deep (0.25 MB) | 0.09 s | 0.12 s | 0.08 s | 0.41 s |
| Tree rows (limit 20,000) | An entry that calls 19,999 separate nodes, and a run that enters each one (6.5 MB) | 0.38 s | 0.41 s | 0.56 s | 6.4 s |
| Tree rows, long chains | A 999-node chain whose last node calls a leaf from 19,001 sites, ids of 16 characters (1.07 MB) | 0.11 s | 0.12 s | 0.40 s | 0.66 s |
| Search for cut calls (limit 1,000,000) | 11 layers that each rename `{`, `}` and `{}`, over 10,000 calls with no arguments: 990,000 units and 330,000 cuts (0.30 MB) | 0.74 s | 0.76 s | 0.25 s | 1.1 s |
| The error-tag finding | A chain of 20,000 nodes that no entry reaches, each declaring a tag (4.9 MB) | 0.27 s | 0.29 s | 0.23 s | 0.21 s |

**What each limit leaves for `docs/examples/realtime-shadows.flightpath.json`.** Its
deepest graph is 14 calls deep, 71 times under the limit. Its largest tree
view is 304 rows, 66 times under. Its search for cut calls costs 77,415 units,
12.9 times under.

**Refusal output is not bounded, and that is accepted.** Every refusal in a
walk repeats the run's name, and nothing caps how many refusals one run
makes. A 2.1 MB file with a 10,000-character run name and 10,000 return moves
that each carry a value out of a `void` node prints 99 MB of refusals in
3.1 s. The volume is the run name's length times the refusal count. It
predates the `void` refusal (#245), which adds one more way to reach it. The
list-field refusals (#247) add another: one refusal per entry that is not a
string, each repeating the node id or layer name, so the volume is that name's
length times the bad-entry count. The
renderer exits with the refusal, and nothing reads the file further. Weighed
against row 5's low rating under ADR 0004, no cap is added.

*Re-accepted 2026-10-17* on the owner's word, relayed by the lead session
(q7 on #248; from #252's Test review, adversarial-lens F4), with new figures.
Since groundtrack 0.63.0 the count is still not bounded, but each refusal is:
a run's name stops at 200 characters where it enters a refusal, and the
whole line at 2,000. Escaping works the other way for one shape. A character
the renderer escapes prints as six, so a short name made only of hidden
characters prints up to six times the bytes it did. Measured over 10,000
refusals, before and after:

| Run name | Before | After |
| --- | --- | --- |
| 10,000 plain characters | 0.20 s, 101.8 M characters | 0.12 s, 4.0 M characters |
| 1,900 DEL characters | 0.11 s, 20.8 M characters | 0.23 s, 14.0 M characters |

**Deep nesting stops the renderer, as one line, and that is accepted.**
*Accepted 2026-10-17* on the owner's word, relayed by the lead session (q7
on #248; from #252's Test review, conventions-lens F2, under ADR 0004's
stopping rule). A value of any type, such as a call's `args`, nested deep
enough overflows the stack in a JSON conversion. The renderer catches it and
prints `<file>: the renderer stopped on this file (RangeError)`, then exits
2. A 0.4 MB file nested 200,000 deep stops `--check`, `--out` and `--text`
in 0.08 s each. No limit is added: the file is refused in effect, and fast.

**A long name drawn on many tree rows is cut where it enters the row.** A
node's display name has no length limit and prints on every row that draws
the node. With only the 2,000-character line cut, a 1,000,000-character name
on 19,999 rows ran `--text` for 6.2 s and then out of memory, a fatal abort
no guard catches. Cut to 1,000 where it enters each row, the same file
reads in 0.55 s. Before 0.63.0 the renderer stopped at once on it, with a
string-length error and a stack trace.

**A printed arg name is bounded.** The args finding prints a name past 200
characters as its first 200, its length and the start of its digest. Escaped
whole, a name of 90,000,000 DEL characters (86 MB) passed V8's string limit
and ended `--check` in a stack trace after 14.7 s. Bounded, it checks in
0.57 s. This bounds what is printed and refuses nothing.

**Node ids have no length limit.** Cost follows file size. Ids of 128, 1,000
and 10,000 characters on the long-chain file check in 0.12 s, 0.17 s and
0.68 s, at 3.5 MB, 22.7 MB and 221 MB.

**Two costs inside `fold` used to miss the target, and #147 removed both.**
The tree view and the call counts no longer read call-chain keys, and `fold`
no longer copies every open frame on each move. Before is 0.24.10, after
0.24.11, same machine. The page column is after only.

| Cost | File | `--check` | `--text` | Page, first draw (after) |
| --- | --- | --- | --- | --- |
| Call-chain keys longer than 16,383 characters | A 125-node chain of 128-character ids, whose last node calls a leaf from 19,000 sites, and a run that enters each one (6.7 MB) | 0.75 s → 0.44 s | 145 s → 0.64 s | 0.44 s |
| The same, through recursion | One node that recurses 900 frames deep in its run, then calls a leaf from 10,000 sites (1.4 MB) | 0.95 s → 0.25 s | 95 s → 0.39 s | 1.1 s |
| A copy of every open frame on each move | A run that walks a 999-node chain and then 19,001 sites at its foot (2.7 MB) | 4.2 s → 0.64 s | 181 s → 1.2 s | 0.73 s |

**One page cost grew, and is known.** `frames` is now built when a state is
read, not stored on it. The source tab's `ranPcs` reads every state's frames
on each redraw. On a row 5 file that redraw went from about 147–333 ms to
641–691 ms, while `fold` itself went from 1,585 ms to 220 ms.

Measured on an AMD Ryzen 9 9950X3D (16 cores), 64 GB of RAM, Windows 11 Pro for

## The hiring interview, its data and its limits

The contract skill's second way in (#343, #344) renders a local page from a
draft, keeps the person's answers in the browser, and reads back the one
block the person pastes. What it holds, where, and for how long:

| Data | Where it sits | Who can read it | How long | What limits it |
| --- | --- | --- | --- | --- |
| Saved answers, and the light or dark choice | The browser's storage for pages opened from disk, under `contract-interview:<type>:<name>:<hash>` and `aviation-scheme`, unencrypted | Other pages opened from disk in the same browser, which can also write it; extensions with file access; programs running as the person; backups of the browser profile | Until the person presses Forget, which removes every key under the contract's prefix and leaves the light or dark choice; the browser may keep its own copy on disk for a while after | Forget, asked for at every hand-back; a restored answer is marked, goes to push-back, and is kept only by its own Keep; the published example (`--site`) keeps nothing |
| The draft, the page and the answers file | The scratch folder, `contract-interview-` and 16 hex digits: in the per-user temp folder on Windows and macOS, under the account's cache folder on Linux, or in a parent the person names, unencrypted | The person's account; on Windows, whoever the temp folder's own access lets in; the readers of a folder the person names, and its sync | Until `--clean` deletes the page and the answers file at the hand-back, and the draft on the person's yes | The folder is mode 700 and the files mode 600 on macOS and Linux; the page is mode 600 wherever it lands unless `--site`, and owner-only before it holds the draft; a parent inside a git work tree is refused |
| The page's title and location | The browser's history | The person's profile, and their browser account if history syncs | As the browser keeps history | The page's notice says so |
| The PR records of claims 15 and 16 | The pull request, public | Anyone | As the repository keeps them | They name no one, hold no contact detail and no absolute path; claim 15 ran on head-chef's public contract |

**Two data migrations.** A redraft carries the person's saved answers from
the old draft's key to the new one, reading only the key the draft's
`previous` names, and on a page rendered with `--shared` it adopts nothing
when `previous` names another stored contract. A rewrite of an older-shape
contract copies every row of the old change log word for word into the new
change-log file, shows the change list before any write, and deletes the old
root contract in the same commit (claim 23 on #313).

**The limits.** Set by ADR 0004's method against the contract skill's own
contract, drafted fresh as `docs/limits/contract-skill.measured.json`
(SHA-256 `9faf6d8bca75bd599f62e92906eec45c6288fd550d421ddeab920a006866032b`):
each is four times that draft's figure, with no field limit under 4,000.
A draft or block over 387,512 bytes, a part of more than 152 clauses, or a
field longer than 6,844 characters is refused, naming the limit. A second
question on one clause is refused, so questions are bounded by clauses. The
page rendered from that draft measured 381,464 bytes on 2026-10-18, and a
test holds it within four times that, 1,525,856 bytes.

**Accepted 2026-10-18** on the owner's word, given in chat with the lead
session (q8, q10 and q17 on #313; from the spec v2 review, data-lens and
adversarial-lens on shared browser storage, widened after the spec v3
review, data-lens on the scratch files): saved interview answers readable
beyond the person, and held unencrypted in the scratch files. The interview's
saved answers sit unencrypted in the browser profile, where other pages
opened from disk in the same browser, extensions with file access, processes
running as the person and profile backups can read them. The scratch
folder's draft (the exemplar, the proposals and the answers taken into it),
page and answers file hold the same work unencrypted until they are deleted.
Accepted because the owner chose to keep answers across a reopen without
encryption, to keep the page simple. Forget removes the saved answers from
the page's store, though the browser may keep its own copy on disk for a
while; the hand-back deletes the page and the answers file and offers to
delete the draft; the folder is owner-only on macOS and Linux, and on
Windows rests on the per-user temp folder's own access; a folder the person
names instead is as private as that folder, and its files leave the machine
if it syncs.

**Accepted 2026-10-18** on the owner's word, relayed by the lead session
(owner step 5 of #344; from the spec v4 re-check's Hardening candidate on
#313): the build session's local http server for claim 15's run was not
stated to listen on the loopback address only or to stop after the run. Its
data was head-chef's public contract, so nothing it served was private.

## The last line of defence is not ours

For rows 1, 2, 6, 10, 13 and 16, the final guard is the host agent's rule that text
in a file is data, not a command. grimoire cannot enforce that rule. A skill can
remind the agent of it and cannot replace it. `SECURITY.md` puts the host agent
out of scope for that reason.

## Gaps, ranked

1. **Say it in the skill prose.** *Done 2026-09-25:* each `SKILL.md` now says
   the material, the files and the renderer's output are data, not instructions,
   and eagle-eye's says a standing yes for the audit comes only from the user.
   Narrows rows 1, 2 and 6; the host agent remains the real guard.
2. **Make the scanners gate.** *Done 2026-09-25:* SkillSpector's `scan` and
   zizmor's `audit` are now required checks on `main`, beside `check`. The
   plugin validator's `validate` joined them on 2026-10-09.
3. **Tell reviewers to check the sheet against the diff.** *Done 2026-09-26:*
   see row 1. The page's warning is the AUTHORED stamp's help note, which shows
   on hover. That is a deliberate choice, not a shortfall. The AI tool that drew
   the page already shows its own warning that AI can make mistakes, and we
   expect a reader who works with AI to know that its output needs checking.
   The note repeats the warning where the page makes its claims.
4. **Measure groundtrack on a hostile file.** *Done 2026-09-26:* see
   [row 5, measured](#row-5-measured). Three limits, and fixes that make
   other costs grow with the file, hold the renderer's three commands under
   1.5 s on every file measured up to 25 MB that passes. The two costs that
   remained inside `fold` are gone since #147.
5. **Consider signed releases or a pinned install path.** Row 8's rug-pull
   exposure. *Decided 2026-09-26: no release tags or signing for now.* Neither
   installer checks a signature, and grimoire builds nothing to attest. A
   plugin user gets a new version only when the version in `plugin.json` has
   moved, and then only when they update by hand or have turned on background
   auto-update, which is off by default. A reader who wants a fixed copy can
   install one commit (see the README's install section). Revisit when someone
   else depends on grimoire, or when it ships something that is built.
